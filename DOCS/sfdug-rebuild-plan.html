SFDUG Rebuild Plan

The current site runs conference software to publish a monthly meetup archive. We rebuild it on a clean Drupal CMS 2 install with three content types, keep the 2026 theme untouched, and migrate the content that matters.

All seven phases are done. The site runs at sfdug-2026-refactor.ddev.site with 79 meetings, 5 people, 48 recordings and the Home node in place; /, /meetings, /upcoming, /people and /videos all render, and a fresh crawl of eight pages logs zero errors and zero warnings. Modules are down from 116 to 94 and config objects from 734 to 592.

01

Why rebuild rather than cut

The site began from a conference recipe that didn't fit. What it left behind is a session-submission and moderation platform — registration, ratings, sponsorships, BOFs, trainings, job listings — sitting on top of a site whose entire public surface is four destinations: /upcoming, /meetings, /people, and the #about / #join anchors on the front page.

Unwinding that means auditing 734 config objects and hoping nothing depends on what you removed. Rebuilding means writing three content types. The content is small enough that the second is faster and lands somewhere you can reason about.

The evidence that settled the content model

Sessions and events are the same thing here. 72 dated sessions occupy 72 distinct dates, spanning 2013-10-14 to 2026-08-20 — not one collision in thirteen years. That is one talk per monthly meeting, not a multi-track schedule.

Discarded, not migrated

The six event nodes are recipe residue, not a parallel model: three are unpublished drafts, and all six carry field_event_date = 1969-12-31 16:33:45 — a broken near-epoch timestamp. The three published ones ("October 2025: Drupal CMS Launch Party", "November 2025: AI and Drupal", "December 2025: Holiday Social") are meetings that belong in the archive as sessions.

One bug turned up while tracing this. The current site's system.site.front is /node, so / serves the frontpage view and the About and Join sections never render — they appear only at /home. The rebuild sets page.front: /home, which fixes it.

The theme settles the rest. sfdug is core_version_requirement: ^11 on base theme stable9 with no contrib dependencies — it ports to 11.4 as-is. So field machine names carry over unchanged, and the templates keep working. That also reframes the field audit: nine empty fields are actively rendered by the templates. They aren't dead, they're designed and not yet filled in.

The two new fields, and why they earn their place

Meetings are online now, with in-person a live possibility. field_event_mode is a list — Online / In person / Hybrid, defaulting to Online — and field_location is plain text, empty until you book a room.

The mode field also fixes something. The theme emits schema.org Event JSON-LD, and today it decides attendance mode by string-sniffing a taxonomy term name:

// sfdug.theme:355 — replaced by field_event_mode $is_online = $venue_name === '' || stripos($venue_name, 'online') !== FALSE || stripos($venue_name, 'zoom') !== FALSE || stripos($venue_name, 'virtual') !== FALSE;

Name a venue "Zoom Room at Twitter HQ" and Google is told an in-person meeting is virtual. Dropping the venue vocabulary makes the structured data more correct, not less.

03

The sfdug site template

Drupal CMS 2 replaced the old per-feature recipes with site templates, and ships drupal_cms_site_template_base — "Blank" — explicitly to be copied. Copy it to recipes/sfdug/ and install the site from it once. Every enabled module is then a line someone chose, in a file you can review.

Blank already carries what we want: drupal_cms_admin_ui, drupal_cms_media, drupal_cms_seo_basic, drupal_cms_anti_spam, drupal_cms_authentication, drupal_cms_privacy_basic, and the core maintenance and performance recipes. Three edits turn it into ours.

# recipes/sfdug/recipe.yml name: SFDUG description: 'San Francisco Drupal Users Group — monthly meetings, speakers, video archive.' type: Site recipes: // unchanged from Blank — admin_ui, media, seo_basic, anti_spam, // authentication, privacy_basic, easy_email_express, core recipes install: - drupal_cms_helper - stark - canvas # not in Blank; must be named explicitly - canvas_stark # "MUST be installed or Canvas breaks in strange ways" - sfdug # our theme, replacing the generated `blank` - views - smart_date # field_session_date is a smartdate; not in Drupal CMS 2 config: strict: false actions: system.site: simpleConfigUpdate: page.front: '/home' system.theme: simpleConfigUpdate: default: 'sfdug'
Corrected after the install

An earlier draft of this plan said we would avoid drupal_cms_content_type_base and the bpmn_io / eca_* / modeler_api / scheduler / linkit / autosave_form family with it. That was wrong. It is applied transitively, and not naming it in our recipe changes nothing:

drupal_cms_media → drupal_cms_privacy_basic → drupal_cms_content_type_base

Both media and privacy_basic are in Blank's list, and both earn their place. Keeping ECA out would mean dropping them and wiring core's media type recipes by hand — more divergence from stock Drupal CMS than the modules are worth.

Decision: accept it. The eight ECA models that arrive are Drupal CMS plumbing, not workflow debt — remote_video_consent, grant_media_type_permissions, unpublished_404, auth_redirects, content_duplicate, privacy_setting_link, define_breakpoints, content_template_disable_preview. Nothing resembling the fifteen session-submission models. The first of those is worth having on a site built around 48 YouTube embeds.

Still worth naming explicitly

canvas and canvas_stark. Blank does not install Canvas, so our recipe names it directly. canvas_stark is easy to miss: it ships inside the module at web/modules/contrib/canvas/themes/canvas_stark, not in web/themes/contrib.

04

Migration

The one thing that must not go wrong

Do not migrate from the existing CSVs. sfdug_nodes_parsed_enriched.csv holds 1,814 scraped rows that became 79 nodes — and three repair passes ran after that import: apply_meetup_dates.php (documented as the "preferred date source"), backfill_session_dates.php, and rematch_session_videos.php. import_2026_content.php then hand-built the 2026 season, the speakers and the Home node. None of that is in the CSVs. Re-running the original migration would silently roll all of it back.

The current database is the source of truth.

Migrate rather than a one-shot script, because the field mapping will want two or three passes and rollback matters. Three CSVs, exported fresh from the live database and already shaped to the new model, run in dependency order.

OrderMigrationSourceRows
1sfdug_peoplepeople.csv — exported from node_field_data + person fields5
2sfdug_videosvideos.csv — remote_video media, current URLs48
3sfdug_meetingsmeetings.csv — references both of the above79

The seven undated sessions migrate as they are, dates empty — legacy titles like "SFDUG - Date TBD - Solr in Drupal 8/9" that are still real talks.

Files move separately: field_photo and field_social_media_card are file fields, and restore_files.php establishes that assets live under public://sfdug/.

When it lands, uninstall migrate, migrate_plus, migrate_tools and migrate_source_csv so they don't settle into the enabled list the way they did last time.

Build sequence

1

Scaffold

git init in sfdug-2026-refactor and commit the pristine Drupal CMS 2.1.4 download before anything is applied, so every later change is a reviewable diff.

Drop the database first. An install was started there and abandoned — 11 tables, users and key_value present, no node tables, and the site still routes to /core/install.php. The recipe should apply to an empty database, not that.

Port the DevPanel scaffolding in the same commit — .devpanel/, .devcontainer/, .envrc, .github/, drush/, logs/, and the post-drupal-scaffold-cmd hook that patches settings.php. The plain download has none of it, and the PR target needs all of it.

07

Still open

The #about and #join sections

Both live on the front page as anchors, and four of the five main-menu links point at them. Where that copy currently comes from — the Home node body, a block, or the template — decides whether it migrates or gets rebuilt.

/videos overlaps /meetings

Two views over the same archive. Worth deciding whether both survive the rebuild or one path redirects to the other.

Canvas on the front page

Canvas is installed and available. The front page is currently assembled from four view blocks in a custom theme, so there is nothing for it to build yet — but it is there when you want it.

PR target: cellear/sfdug_drupalforge

A DevPanel installer repo, default branch main, last touched 7 Aug 2026. It carries scaffolding the fresh Drupal CMS download does not, and has no recipes/ directory — so recipes/sfdug/ arrives as new, and its composer.json will need the recipe installer path. Worth a look before the PR, not before the build.

What happens to the old site

sfdug_df_simplified stays as the source of truth until the rebuild is verified. After that: archive the branch, or keep it running until DNS moves.
